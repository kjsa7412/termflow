GITHUB ACTIONS · TERMFLOW · CR-17

TermFlow CI/CD 흐름

코드를 push하면 실행이 하나 생깁니다. 그 실행이 검사를 하고, 판을 올린 push라면 검사가 끝난 뒤 v1.2.2 배포물처럼 판이 앞에 붙은 별도 실행이 오프라인 설치 번들과 GitHub Release 초안을 만듭니다. 문서만 바꾼 push는 실행이 생기지 않습니다. 판 번호의 원천은 package.json의 version 하나이고, 태그는 사람이 달지 않습니다.

ci.yml release.yml auto-release.yml (삭제)

한눈에

배포는 판으로 구분평소 커밋은 커밋 메시지 제목의 ci 실행 하나, 배포는 v1.2.2 배포물 실행으로 따로 보입니다.
문서만의 push는 실행 없음docs·루트 .md만 바꾸면 돌지 않습니다. 제품에 들어가는 설명서 두 권과 그림은 예외입니다.
판 올림만 배포물평소 커밋은 배포물 요청이 건너뜀으로 남고, 판을 올린 커밋만 번들을 만듭니다.
자동화는 초안까지Release 게시와 서버 반영은 사람이 확인하고 합니다.

단계별 설명

1

개발자: 커밋하고 main에 push

git push origin main

평소 커밋은 그냥 push합니다. 판을 올릴 때만 세 곳을 한 커밋에서 함께 고칩니다.

  • package.json의 version
  • docker-compose.yml의 이미지 태그 termflow-app:<판>
  • docs/릴리스_노트_v<판>.md

판 올림 커밋 메시지는 v1.2.2 — 판 올림 · 요약처럼 판으로 시작합니다. push 전에 bash scripts/release-check.sh로 세 값이 맞는지 로컬에서 확인합니다. CI의 판 확인도 같은 스크립트를 씁니다.

실행이 생기지 않는 push는 docs/, 루트의 .md, 개발 도구 폴더만 바꾼 경우입니다. docs/사용자_가이드.md·docs/설치_운영_가이드.md·docs/img/는 웹 빌드가 제품 내 설명서(/manual)로 싣기 때문에 바꾸면 CI가 돕니다.

2

ci.yml: 검사

on: push(main, stage/**) · pull_request(main) · workflow_dispatch, 문서만의 변경 제외

lint · typecheck가 관문입니다. 가장 빨리 끝나는 검사라 먼저 돌리고, 실패하면 무거운 작업 네 개를 시작하지 않습니다. 설치 스크립트 검사와 판 확인은 의존 없이 처음부터 나란히 돕니다.

작업하는 일선행제한
lint · typecheckeslint · prettier · check:no-ai · tsc없음15분
설치 스크립트 검사shellcheck(install.sh · start.sh · scripts/*.sh), PowerShell 구문 파싱없음5분
test(단위)shared · web · server · site 단위 테스트lint20분
test:dbTestcontainers postgres:17, 실행마다 새 컨테이너lint40분
buildshared → web → server, site 누출 검사lint20분
이미지 · Linux 설치docker build → install.sh(승계 1~12 · 대사 · DDL 회귀) → /health · /manual → 백업 · 복구lint40분
  • 브랜치와 PR은 새 push가 오면 진행 중인 실행을 취소합니다. main은 취소하지 않고 순서대로 돕니다. 배포물을 만드는 중에 끊기지 않게 하려는 것입니다.
  • 설치 작업이 실패하면 compose 로그 · migration/report/를 7일 보관 산출물로 올립니다.
  • E2E(Playwright)는 dev DB와 설치된 Chrome · Edge가 필요해 CI가 아니라 로컬 게이트에서 돌립니다.
3

ci.yml: 판 확인과 배포물 요청

jobs: version(판 확인) → release(배포물 요청, needs: 검사 6개 + 판 확인)

main push일 때만 판 확인이 package.json version을 읽고 원격에 v<version> 태그가 있는지 봅니다.

  • 태그가 있음: 판을 올리지 않은 평소 커밋입니다. release 작업은 건너뜀으로 끝납니다.
  • 태그가 없음: 판을 올린 커밋입니다. 그 자리에서 release-check.sh로 판 번호를 맞춰 보고, 어긋나면 검사를 기다리지 않고 바로 실패합니다. 검사 6개가 모두 통과하면 배포물 요청 작업이 release.yml을 판과 커밋을 넣어 실행합니다.

판 확인을 CI 안에 둔 이유: 예전에는 CI가 끝날 때마다 별도 워크플로(auto-release)가 깨어나 태그를 확인했습니다. 할 일이 없을 때도 실행이 하나씩 쌓였습니다. 지금은 판 확인이 CI의 작업 하나이고, 판을 올렸을 때만 배포물 실행이 새로 생깁니다.

평소 ci 실행 제목에 판이 없는 이유: 실행 제목은 실행이 시작될 때 정해져서 package.json을 읽을 수 없습니다. 그래서 판을 입력으로 받는 배포물 실행에만 판을 붙입니다.

4

release.yml: 번들을 만들고 태그와 Release 초안

on: workflow_dispatch(tag, sha) · run-name: "<tag> 배포물" — jobs: meta → bundle → publish

평소에는 3단계의 요청으로만 돌고, Actions 목록에 v1.2.2 배포물로 보입니다. 이미 있는 태그로 배포물을 다시 만들 때는 Actions › release › Run workflow에서 tag만 넣어 실행하고, 목록에는 v1.2.1 배포물 다시 만들기로 보입니다.

작업하는 일
판 번호 확인package.json version = compose 이미지 태그, 릴리스 노트가 있는지 확인
번들 · 오프라인 설치 확인docker build → bundle.sh → 빌드한 이미지와 postgres:17을 지움 → 번들을 새 폴더에 풀어 install.sh → 설치된 이미지 ID가 번들의 이미지와 같은지 확인 → /health
태그 · Release 초안판 올림 커밋에 v<판> 태그를 만들고(커밋 목록에서 그 커밋 옆에 판이 표시됨, 뒤에 같이 push한 커밋이 제품 파일을 바꿨으면 끝 커밋), sha256을 확인한 뒤 termflow-linux-<판>.tar.gz와 .sha256을 초안(draft)으로 올림. 같은 판이 이미 있으면 파일만 교체

태그를 마지막에 만드는 이유: 번들이 실패하면 태그가 생기지 않습니다. 그래서 고친 커밋을 push하면 판 확인이 다시 "태그 없음"을 보고 배포물을 다시 시도합니다. 실패한 판에 태그만 남는 일이 없습니다.

번들 검사의 의도: 설치할 서버에는 레지스트리도 소스 빌드도 없습니다. 그래서 러너에서 이미지를 일부러 지우고 번들 안의 images/만으로 설치되는지 확인합니다.

번들에는 승계 원본(seed/original)이 들어 있어서 저장소와 Release는 비공개로 둡니다.

5

사람: 게시하고 서버에 반영

초안의 파일과 릴리스 노트를 확인한 뒤 Release를 게시합니다. 서버에는 번들을 옮겨 upgrade.sh로 올리고, 기동 로그에서 기본 표준 템플릿 상태 줄로 적용 여부를 확인합니다. 이 단계는 자동화하지 않았습니다.

개편 전과 비교

상황개편 전지금
문서만 바꾼 pushci 약 5분 + auto-release 약 8초, 실행 2개실행 없음
평소 코드 pushci + auto-release(할 일 없이 종료), 실행 2개ci 실행 1개, release 작업은 건너뜀
판을 올린 pushci 실행 + auto-release 실행 안에 release 작업ci 실행(검사) + v<판> 배포물 실행
배포 실행 찾기auto-release 실행을 하나씩 열어 봐야 함목록 제목 앞의 판(v1.2.2 배포물)으로 바로 구분
태그를 만드는 시점번들 전(번들 실패 시 태그만 남음)번들 검증 뒤
release 시작 경로자동 호출 · 손 태그 push · 수동 실행자동 호출 · 수동 실행(태그 push 경로 삭제)

Actions 왼쪽 목록의 auto-release는 예전 실행 기록이 남아 있어서 보입니다. 그 실행들을 지우면 목록에서도 사라집니다. release는 수동 실행 버튼 때문에 목록에 남습니다.

개편 전 기록: auto-release #7은 왜 돌았나

v1.2.1 배포물을 만든 실행입니다. 판을 올린 커밋 fb2cd93과 TODO 커밋 65f77fb를 한 번에 push했습니다(10월 6일 10:16, 6fae4e1 → 65f77fb). GitHub는 push 한 번에 마지막 커밋의 CI만 돌리므로 fb2cd93의 CI 실행은 없습니다. 65f77fb의 CI(#14)가 통과하자 auto-release가 v1.2.1 태그가 없음을 보고 65f77fb에 태그를 달고 번들을 만들었습니다. 두 커밋 사이 차이는 TODO 문서뿐이라 번들 내용은 같습니다.
