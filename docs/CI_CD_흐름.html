GITHUB ACTIONS · TERMFLOW

TermFlow CI/CD 흐름

커밋 하나가 검사를 거쳐 오프라인 설치 번들과 GitHub Release 초안이 되기까지의 길입니다. 워크플로는 세 개이고, 판 번호의 원천은 package.json의 version 하나입니다. 태그는 사람이 달지 않습니다.

ci.yml auto-release.yml release.yml

한눈에

CI는 모든 push에서main·stage/** push와 main 대상 PR마다 ci.yml이 6개 잡으로 검사합니다.
판을 올린 커밋만 릴리스version을 바꾸지 않은 커밋은 auto-release가 바로 끝냅니다.
검사는 한 번만자동 경로는 같은 커밋의 CI 통과를 근거로 release 안의 ci를 건너뜁니다.
자동화는 초안까지Release 게시와 서버 반영은 사람이 확인하고 합니다.

단계별 설명

1

개발자: 커밋하고 main에 push

git push origin main

평소 커밋은 그냥 push합니다. 판을 올릴 때만 세 곳을 한 커밋에서 함께 고칩니다.

  • package.json의 version
  • docker-compose.yml의 이미지 태그 termflow-app:<판>
  • docs/릴리스_노트_v<판>.md

push 전에 bash scripts/release-check.sh로 세 값이 맞는지 로컬에서 확인합니다. CI의 판 번호 검사도 같은 스크립트를 씁니다.

2

ci.yml: 6개 잡으로 검사

on: push(main, stage/**) · pull_request · workflow_dispatch · workflow_call

lint · typecheck가 관문입니다. 가장 빨리 끝나는 검사라 먼저 돌리고, 실패하면 무거운 잡 네 개를 시작하지 않습니다. 설치 스크립트 검사는 의존 없이 처음부터 나란히 돕니다.

잡하는 일선행제한
lint · typecheckeslint · prettier · check:no-ai · tsc없음15분
설치 스크립트 검사shellcheck(install.sh · start.sh · scripts/*.sh), PowerShell 구문 파싱없음5분
test(단위)shared · web · server · site 단위 테스트lint20분
test:dbTestcontainers postgres:17, 실행마다 새 컨테이너lint40분
buildshared → web → server, site 누출 검사lint20분
이미지 · Linux 설치docker build → install.sh(승계 1~12 · 대사 · DDL 회귀) → /health · /manual → 백업 · 복구lint40분
  • 같은 ref에 새 push가 오면 진행 중인 CI를 취소합니다(cancel-in-progress: true).
  • 설치 잡이 실패하면 compose 로그 · migration/report/를 7일 보관 산출물로 올립니다.
  • E2E(Playwright)는 dev DB와 설치된 Chrome · Edge가 필요해 CI가 아니라 로컬 게이트에서 돌립니다.
3

auto-release.yml: 판이 바뀌었는지 판단

on: workflow_run(ci, completed, main) · 조건: 성공 + push 이벤트

main의 CI가 성공하면 그 커밋의 package.json version을 읽고, 원격에 v<version> 태그가 있는지 봅니다.

  • 태그가 있음: 판을 올리지 않은 평소 커밋입니다. 여기서 끝납니다.
  • 태그가 없음: 판을 올린 커밋입니다. release-check.sh로 판 번호를 다시 맞춰 보고, 그 커밋에 태그를 만든 뒤 release.yml을 skip_ci: true로 부릅니다.

왜 직접 부르나: GITHUB_TOKEN으로 만든 태그 push는 다른 워크플로를 깨우지 않습니다. 그래서 release.yml의 태그 트리거에 기대지 않고 workflow_call로 바로 호출합니다.

4

release.yml: 번들을 만들고 Release 초안 올리기

jobs: meta → ci → bundle → publish

시작하는 길은 세 가지입니다. 기본은 3단계의 자동 호출이고, 손으로 v* 태그를 push하거나 Actions 화면에서 수동 실행해도 됩니다. 자동 호출일 때만 ci를 건너뜁니다.

잡하는 일
판 번호 확인태그 = package.json version = compose 이미지 태그, 릴리스 노트가 있는지 확인
cici.yml 전체를 태그 커밋으로 다시 실행. 자동 경로(skip_ci)면 건너뜀
번들 · 오프라인 설치 확인docker build → bundle.sh → 빌드한 이미지와 postgres:17을 지움 → 번들을 새 폴더에 풀어 install.sh → 설치된 이미지 ID가 번들의 이미지와 같은지 확인 → /health
Release 초안sha256 확인 뒤 termflow-linux-<판>.tar.gz와 .sha256을 초안(draft)으로 올림. 같은 판이 이미 있으면 파일만 교체

번들 검사의 의도: 설치할 서버에는 레지스트리도 소스 빌드도 없습니다. 그래서 러너에서 이미지를 일부러 지우고, 번들 안의 images/만으로 설치되는지 확인합니다. 이미지 ID까지 맞춰 봐서 몰래 다시 빌드되는 경우도 잡아냅니다.

번들에는 승계 원본(seed/original)이 들어 있어서 저장소와 Release는 비공개로 둡니다.

5

사람: 게시하고 서버에 반영

초안의 파일과 릴리스 노트를 확인한 뒤 Release를 게시합니다. 서버에는 번들을 옮겨 upgrade.sh로 올리고, 기동 로그에서 기본 표준 템플릿 상태 줄로 적용 여부를 확인합니다. 이 단계는 자동화하지 않았습니다.

실행 auto-release #7 읽기

커밋 65f77fb(v1.2.1 TODO 체크)의 main CI가 통과해 시작된 실행입니다. 전체 3분 12초에 성공했고, 태그 v1.2.1은 이 커밋에 달렸습니다.

판을 올린 커밋은 바로 앞의 fb2cd93인데 태그가 그 뒤 커밋에 달린 이유는 두 커밋을 한 번에 push했기 때문입니다(10월 6일 10:16, 6fae4e1 → 65f77fb). GitHub는 push 한 번에 마지막 커밋의 CI만 돌리므로 fb2cd93의 CI 실행은 없고, v1.2.1 태그가 없는 상태에서 처음 성공한 CI가 65f77fb의 것이었습니다. 두 커밋 사이 차이는 TODO 문서뿐이라 번들 내용은 같습니다.

잡결과시간설명
판 태그성공6s태그 존재 여부 확인, 필요하면 생성

화면에서 ci 아래 잡들이 빈 원으로 보이는 건 실패가 아니라 건너뛴 것입니다. 검사는 바로 앞의 main CI 실행에서 이미 끝났습니다.
