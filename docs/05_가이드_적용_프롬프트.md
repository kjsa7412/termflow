# 기존 프로젝트에 테이블 설계 가이드 적용 — 에이전트 프롬프트

- 대상: 이미 테이블을 설계한 TermFlow 프로젝트(예: DPMS)를 [테이블 설계 가이드](04_테이블_설계_가이드.md) 기준으로 고치는 작업
- 사용법: 아래 1~3단계 프롬프트를 **한 단계씩** 에이전트에게 보낸다. 앞 단계 결과를 사용자가 확인한 뒤 다음 단계를 보낸다.
- `{프로젝트키}`는 실제 키(예: `DPMS`)로 바꾼다.

## 준비 (사용자)

- [ ] TermFlow 서버가 **v1.3.5 이상**이다(가이드 검증 경고 v1.3.4, 스킬 파일 내려받기 v1.3.5). 경고가 테이블별 위반을 직접 알려 주므로 점검이 판단에 덜 의존한다.
- [ ] 에이전트 클라이언트에 TermFlow 설계 절차 스킬이 설치되어 있고(서버의 `/downloads/termflow-table-design/SKILL.md` — [사용자 가이드 §9.5](사용자_가이드.md)), `/mcp`가 연결되어 있다. 스킬은 서버 판과 같은 판을 받는다.
- [ ] 프로젝트 설정 "기본컬럼 포함"이 켜져 있다(`project_settings_get`의 `includeDefaultCols`). 꺼져 있으면 기본컬럼 누락 경고가 나오지 않으므로 켜거나, 1단계에서 직접 확인하게 한다.
- [ ] 토큰 주인이 그 프로젝트의 **프로젝트 관리자(ADMIN)**다. 도메인·코드구분·도메인분류 등록과 용어 바로 승인에 필요하다.
- [ ] (권장) 수정 전 DDL을 받아 둔다. 고친 뒤 DDL과 비교해 실제 DB 변경분을 뽑을 때 쓴다. 1단계 프롬프트에 포함되어 있다.

---

## 1단계 — 점검만 (수정 금지)

```markdown
TermFlow 프로젝트 {프로젝트키}의 모든 테이블을 TermFlow 테이블 설계 가이드(설계 절차) 기준으로 점검하라.

규칙
- 이 단계에서는 아무것도 등록·수정·삭제하지 마라. 조회 도구와 table_validate만 쓴다.
- 판단 기준은 가이드다. 가이드에 없는 기준을 만들지 마라. 애매하면 "판단 필요"로 표시하라.

할 일
1. whoami로 역할을 확인하고, project_settings_get(includeDefaultCols·defaultColSetId)·biz_areas_list·default_column_set_get(기본 세트 컬럼)·domain_classes_list를 읽어라.
2. ddl_generate로 프로젝트 전체 DDL(SQL)을 받아 "수정 전 DDL"로 보여 주거나 파일로 저장하라.
3. tables_list로 전체 테이블과 경고 수(warningCnt)를 보고, 테이블마다 table_get을 실행하라. table_get 응답의 errors·warnings가 저장 검증과 같은 결과다(table_validate를 따로 부르려면 tableId를 함께 넘겨라 — 없으면 자기 이름이 중복으로 잡힌다).
4. 서버 경고로 나오는 위반을 그대로 모아라.
   - W_DEFAULT_COLS_MISSING: 기본 세트 컬럼 누락(가이드 §2.6). 설명에 "기본컬럼 제외"가 있는 테이블은 나오지 않는다 — 그 사유가 맞는지 확인하라.
   - W_MATCH_MANUAL·W_MATCH_SIMILAR: 수동 입력·유사 도메인을 다른 이름으로 씀(§2.2)
   - W_CODE_CLS_NONE: 물리명이 _CD로 끝나는데 코드구분 없음(§2.5). 도메인 있는 코드 마스터 키와 그 참조 컬럼은 나오지 않는다.
   - W_COMPOSED_KEY·W_COMPOSED_SHARED: PK이거나 다른 테이블에도 있는 컬럼이 COMPOSED(§2.3 D1·D2)
   - 그 밖의 경고(W_TERM_*·W_DOMAIN_TYPE_CHANGED·W_DEFAULT_QUOTED 등)
5. 경고로 잡히지 않으니 직접 판단하라.
   - 코드성 접미어(구분·유형·상태·등급·종류·분류·판정)인데 코드구분이 없는 컬럼, 숫자 등급·상태를 INT 도메인으로 둔 컬럼(§2.5-4), 이름이 …코드인데 값이 열린 문자열인 컬럼(§2.5-3)
   - 다른 테이블을 가리키지만 물리명이 달라 공유로 잡히지 않는 참조 컬럼(D1)
   - 접미어 기본 타입과 다른 타입을 쓰는 도메인에 사유가 있는가(§2.4)
   - 같은 의미에 다른 접미어를 섞었는가(예: 시각 TS와 일시 DTS, §2.1-3), 기본컬럼과 역할이 겹치는 컬럼(§2.6-3)
   - PK·기본값·테이블 설명(§2.7·§3)
   - includeDefaultCols가 꺼져 있으면 기본 세트 컬럼 누락
6. 여러 테이블에 공통으로 나오는 컬럼(같은 논리명·물리명)을 따로 모아라.

보고 형식
- 요약: 테이블 수, 위반 테이블 수, 위반 종류별 건수(서버 경고 / 직접 판단 구분)
- 표 1(테이블별): 테이블 | 위반 | 근거(경고 코드 또는 "판단") | 가이드 조항 | 고칠 방법 | 물리명·타입이 바뀌는가(예/아니오)
- 표 2(공통 컬럼): 논리명 | 물리명 | 나오는 테이블 | 현재 matchType | 도메인 등록 필요 여부
- "판단 필요" 항목 목록과 각각 사용자에게 물을 질문
```

**사용자 확인**: 위반 목록이 맞는지, "판단 필요" 항목에 답한다. 고치지 않을 항목이 있으면 다음 단계에 적어 보낸다.

## 2단계 — 표준 사전 등록안 (등록 전 확인)

```markdown
1단계 점검 결과로 TermFlow 프로젝트 {프로젝트키}를 고치는 데 필요한 표준 사전 변경안을 만들어라.

규칙
- 아직 등록하지 마라. 등록안만 보여라.
- 용어: terms_check로 중복을 확인하고, standards_search로 비슷한 용어의 약어 관례를 보고 물리약어를 정하라. 뜻이 같은 기존 용어가 있으면 새로 만들지 말고 그것을 써라.
- 도메인: domain_calculate로 미리 계산한 결과(논리명·물리명·타입)를 그대로 보여라. 접미어 기본 타입과 다른 타입을 쓰려면 가이드 §2.4 순서(다른 접미어 → 도메인분류 변경 → 수동 타입 도메인 + 사유)대로 판단 근거를 적어라.
- 코드구분: 코드값을 모르면 지어내지 말고 질문으로 남겨라.
- 사용자 답변(1단계 확인 내용): {여기에 1단계 답변·제외 항목을 적는다}

보고 형식
- 표 A(용어): 한글명 | 물리약어 | 설명 | 중복 확인 결과
- 표 B(도메인): 논리명 | 조각(nm1..) | 물리명 | 타입 | 수동 타입이면 사유 | 쓰일 테이블·컬럼
- 표 C(코드구분·코드값): 업무구분 | 코드구분명 | 코드값 목록 | 연결할 컬럼
- 표 D(도메인분류, 필요할 때만): 접미어 | 이름 | 타입 | 이유
- 등록 순서(용어 → 도메인분류 → 도메인 → 코드구분)
```

**사용자 확인**: 등록안을 승인하거나 고친다. 코드값 질문에 답한다.

## 3단계 — 등록과 테이블 수정

```markdown
2단계 등록안 중 내가 승인한 내용대로 TermFlow 프로젝트 {프로젝트키}를 고쳐라.

승인 내용: {여기에 승인·수정한 등록안을 적는다. 예: "표 A~C 모두 승인, 표 B의 ○○는 VARCHAR(20)으로"}

규칙
- 승인한 사전 변경만 등록하라. 승인하지 않은 용어·도메인·코드구분은 만들지 마라.
- 테이블은 table_get으로 최신본을 읽고, 기존 행의 columnId를 유지한 전체 columns와 version으로 table_save 하라. 409 E_VERSION_CONFLICT면 다시 읽어 합쳐라.
- 컬럼은 다시 columns_autocomplete로 받은 결과를 써라. 물리명·타입을 손으로 짓지 마라.
- 기본컬럼은 table_save가 자동으로 넣지 않는다. default_column_set_get의 컬럼을 세트 순서대로 끝에 넣어라(defaultColId 유지, matchType DEFAULT, columnId null). 같은 물리명 컬럼이 defaultColId 없이 이미 있으면 그 행을 기본컬럼 행으로 바꿔라(물리명·타입이 다르면 변경 목록에 넣는다). 사용자가 제외를 지시한 테이블은 설명에 "기본컬럼 제외: <사유>"를 적어라.
- **물리명이나 타입이 바뀌는 컬럼은 고치기 전에 목록으로 보여 주고 내 확인을 받아라.** 실제 DB와 애플리케이션 코드에 영향이 있다. 기본컬럼 추가·도메인 연결·코드구분 연결처럼 물리명과 타입이 그대로인 변경은 확인 없이 진행해도 된다.
- 테이블마다 저장 전에 table_validate(tableId 포함)로 오류 0·경고 0을 만들어라. 1단계 4번의 설계 경고가 남으면 고치지 않은 것이다. 경고를 남겨야 하면 사유를 테이블 설명에 적어라.
- 공통 컬럼은 도메인을 먼저 등록·연결한 뒤 그 컬럼이 나오는 모든 테이블을 같이 고쳐라. 한쪽만 고치면 W_COMPOSED_SHARED가 다른 테이블에 남는다.
- FINAL 테이블은 고치기 전에 알려라.

보고 형식(테이블마다)
- 매칭 통계: EXACT · CODE · COMPOSED · DEFAULT · SIMILAR · MANUAL 건수
- COMPOSED로 남긴 컬럼과 사유(가이드 §2.3)
- 바뀐 컬럼: 이전 → 이후(물리명·타입·matchType)
- 검증 결과(오류·경고 건수, 남긴 경고와 사유)
마지막에
- tables_list로 전체 테이블의 경고 수(warningCnt)가 0인지 다시 확인한 결과
- 등록한 사전 변경 목록
- ddl_generate로 받은 수정 후 DDL과, 수정 전 DDL 대비 실제 DB에 적용할 변경(ALTER 대상) 요약
```

**사용자 확인**: 물리명·타입 변경 목록을 승인한 뒤 진행시킨다. 끝나면 수정 후 DDL로 실제 DB 마이그레이션 여부를 판단한다.

## 되돌리기

테이블은 저장할 때마다 이력이 남는다. 잘못 고친 테이블은 `table_history`로 이전 판을 찾고 `table_restore`로 되돌린다(프로젝트 관리자). 표준 사전 등록은 이력 복원 대상이 아니므로 2단계 확인을 거친다.
